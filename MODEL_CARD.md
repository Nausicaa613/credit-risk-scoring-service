# Model Card: credit-risk-scoring-service

This document follows the spirit and structure of *Model Cards for Model Reporting*
(Mitchell et al., 2019). It documents a portfolio/educational credit risk scorecard
and is intended to be updated by the repository owner whenever the training data,
features, hyperparameters, or threshold change.

### Portfolio / educational statement

This model is a **portfolio and educational artifact**. It is trained on synthetic
data generated by a script in this repository, it has never been validated against
real lending outcomes, and it has not been reviewed by credit risk, model risk
management, compliance, or legal functions. It exists to demonstrate an end-to-end
scoring service: synthetic data generation, from-scratch training, JSON model
artifacts, explainable per-feature contributions, persistence, audit logging, and
observability. It is **not** a production credit model and must not be treated as one.

## 2. Intended use

### 2.1 Primary intended uses

- Demonstrating and teaching the mechanics of a linear WoE/logistic scorecard.
- Serving as a self-contained reference implementation of an explainable scoring API
  (per-feature contributions plus reason codes).
- Benchmarking and profiling a dependency-free Python HTTP service (`make bench`).
- Serving as a starting skeleton for a real scorecard project that will replace the
  synthetic data, add validation, and obtain proper review.

### 2.2 Primary intended users

- Software engineers studying service design, from-scratch ML, or standard-library-only Python.
- Data scientists who want a readable, auditable reference for logistic-scorecard training.
- Reviewers and interviewers evaluating the repository as a portfolio project.

### 2.3 Out-of-scope uses

The following uses are explicitly out of scope and are not supported by this model:

- **Real lending decisions**, including approvals, denials, pricing, limit assignment,
  line increases or decreases, and collections prioritization.
- **Adverse action notices** or any consumer-facing explanation required by law
  (for example ECOA/Regulation B, FCRA, or GDPR Article 22 style rights).
- **Any decision that affects a person**, directly or indirectly, including
  employment, housing, insurance, tenancy, or benefit eligibility.
- Production deployment of any kind, including shadow or champion/challenger scoring
  of real applicants.
- Any use requiring regulatory validation, fair lending testing, or model risk
  management sign-off.

## 3. Factors

### 3.1 Relevant factors

The scorecard consumes the twelve applicant and loan features listed in Section 6.
These are standard credit-risk style inputs: capacity (income, debt-to-income),
stability (employment tenure, credit history length), prior behavior (delinquencies,
revolving utilization), and loan structure (amount, term, purpose).

### 3.2 Demographic and protected attributes — known gap

**The synthetic data generator does NOT model protected attributes.** No race,
ethnicity, sex, gender, marital status, national origin, religion, disability status,
age-as-protected-class treatment, or zip/postal code is generated, recorded, or
consumed by the model. `age` exists as a numeric feature because it appears in
typical credit feature sets, but it is not treated as a protected attribute anywhere
in this repository.

Because no protected attributes are present in the data, **no fairness or
disparate-impact evaluation has been performed**, and none can be performed on this
dataset. There is no measurement of demographic parity, equal opportunity,
equalized odds, predictive parity, or any other group-fairness criterion. This is a
**known gap** and is restated in Sections 8 and 9. Anyone adapting this code for a
decision that affects people must (a) obtain real, lawfully collected data,
(b) define the protected groups and the applicable legal standard, and (c) complete a
fairness and fair-lending review before any use.

## 4. Metrics

The repository's training script (`scripts/train_model.py`, run via `make train`)
reports the following metrics. All classification metrics are computed at the
configured decision threshold on the evaluation split.

  Metric   Definition   Role  
  ---   ---   ---  
  AUC (ROC)   Probability that a randomly chosen positive (default) case is ranked above a randomly chosen negative case.   **Primary ranking metric**  
  KS statistic   Maximum separation between the cumulative default and non-default score distributions.   **Secondary ranking metric**  
  Accuracy   Fraction of evaluation rows classified correctly at the threshold.   Diagnostic  
  Precision   Of rows predicted default, the fraction that are actual defaults.   Diagnostic  
  Recall (sensitivity, TPR)   Of actual defaults, the fraction predicted as default.   Diagnostic  
  F1   Harmonic mean of precision and recall.   Diagnostic  
  Confusion matrix counts   TP, FP, TN, FN at the threshold.   Diagnostic  

Metric meanings in one line each:

- **AUC** — threshold-free measure of how well the model ranks risky applicants above safe ones.
- **KS** — the largest vertical gap between the two score distributions; a credit-industry standard for ranking power.
- **Accuracy** — overall hit rate; misleading under class imbalance, which is expected here.
- **Precision** — cost of false alarms among predicted defaults.
- **Recall** — share of true defaults the model catches.
- **F1** — single-number tradeoff between precision and recall.
- **Confusion matrix** — raw TP/FP/TN/FN counts behind precision, recall, and F1.

## 5. Training data

- **Source:** synthetic data generated by `scripts/generate_dataset.py` from a
  pseudorandom number generator with a **fixed seed**, so runs are reproducible.
- **Size:** `N` samples is configurable on the command line / in configuration; the
  default is chosen to keep training fast. Record the actual value used in Section 4.1.
- **Split:** deterministic train/evaluation split (fixed seed) so reported metrics are
  reproducible.
- **Label:** a binary default flag generated from a latent linear risk function plus
  noise. The generator's coefficients are structural, not estimated.
- **Generator intent:** produce a dataset with a learnable linear signal, mild class
  imbalance, realistic marginal distributions, and a small amount of missing data.

**The data is synthetic.** It contains no real applicants, no real accounts, no real
outcomes, and no real-world signal. It is not a sample from any lending population,
it does not reproduce any known base rate, and any relationship between a feature and
default in this data exists only because the generator was written to create it.
Metrics computed on this data measure how well the model recovers the generator, not
how well it would predict real credit risk.

The generator does not emit protected attributes (Section 3.2).

## 6. Features

All features are numeric or binary after feature engineering. `WoE` indicates the
feature is weight-of-evidence encoded during training; missing values are imputed as
described in `docs/DESIGN.md`.

  Feature   Type   Description   Expected direction of effect on risk  
  ---   ---   ---   ---  
  `age`   integer, years   Applicant age at application.   Older applicants expected slightly lower risk in the synthetic generator; weak effect.  
  `annual_income`   float, currency   Gross annual income before tax.   Higher income expected lower risk (increases capacity).  
  `employment_years`   float, years   Years in current employment.   Longer tenure expected lower risk (stability).  
  `debt_to_income_ratio`   float, ratio   Total monthly debt payments divided by gross monthly income.   Higher ratio expected higher risk.  
  `num_delinquencies_24m`   integer, count   Count of delinquencies in the last 24 months.   More delinquencies expected higher risk.  
  `credit_history_months`   integer, months   Length of the credit file / oldest account age.   Longer history expected lower risk (more information, established behavior).  
  `loan_amount`   float, currency   Requested principal.   Larger amounts expected higher risk (larger exposure), weakly.  
  `loan_term_months`   integer, months   Requested term.   Longer terms expected higher risk in the synthetic generator.  
  `num_open_accounts`   integer, count   Number of currently open tradelines.   Weak, non-monotone effect; more accounts can indicate either established credit or stress.  
  `revolving_utilization`   float, ratio   Revolving balances divided by revolving limits.   Higher utilization expected higher risk.  
  `has_mortgage`   binary (0/1)   Whether the applicant has a mortgage tradeline.   Expected lower risk in the synthetic generator (secured, established credit), though it also raises fixed obligations.  
  `purpose_code`   categorical code   Encoded loan purpose (for example debt consolidation, auto, home improvement).   Direction varies by category; encoded via WoE.  

Feature engineering (ratios, clipping, binning, WoE mapping) is documented in
`docs/DESIGN.md`. The WoE bins are fit on the training split only.

## 8. Ethical considerations

### 8.1 Risks

1. **Automation bias.** A clean JSON API returning a confident probability invites
   downstream users to treat the number as authoritative. The score is a linear
   function of synthetic training data and carries no validated predictive power.
2. **Feedback loops.** If a score like this were used to allocate credit, denied
   applicants would never generate the repayment outcomes needed to correct the
   model; the score would confirm its own training distribution. Nothing in this
   repository breaks that loop.
3. **Proxy discrimination.** Even without protected attributes, features such as
   `annual_income`, `employment_years`, `credit_history_months`, and `has_mortgage`
   correlate with protected characteristics. A model using them can reproduce
   disparate impact without ever reading a protected attribute. Zip-code-like and
   income-like proxies are a recognized fair-lending hazard, and no test in this
   repository would detect it.
4. **Over-trust in linear transparency.** Coefficients, WoE bins, and per-feature
   contributions make the model *look* interpretable. Interpretability is not
   correctness: a transparent model can still be wrong, biased, or miscalibrated,
   and users may skip validation because the math is visible.
5. **Threshold and band arbitrariness.** The decision threshold and band edges are
   configuration constants chosen for illustration. Changing them changes who is
   flagged, with no governance behind the choice.
6. **Data-provenance confusion.** Synthetic results are easy to misquote as real
   performance if the `TBD` placeholders in Section 4.1 are ever replaced by
   illustrative or generator-recovery numbers.

### 8.2 Mitigations

- This model card, the repository README, and the API response all state that the
  model is a portfolio/educational artifact.
- Every score response carries per-feature contributions and reason codes so that a
  human can inspect *why* a score moved, rather than consuming a bare probability.
- The service emits no protected attributes and does not attempt to infer them.
- The `audit_events` table is append-only, providing a tamper-evident record of what
  was scored and why, for review during development.
- Decision thresholds and band edges live in configuration, so any change is explicit
  and reviewable rather than hidden in code.
- Documentation deliberately treats missing fairness analysis as a first-class known
  gap rather than an implicit assumption of safety.
- Anyone repurposing this code for a human-affecting decision must replace the data,
  rerun training, complete the fairness and calibration work, and obtain review before
  deployment. The repository provides none of that gating.

## 9. Caveats and recommendations

1. **Do not use this model for real credit decisions** or any decision that affects a
   person. It has not been validated, reviewed, or approved.
2. **The training data is synthetic.** It contains no real-world signal; metrics
   measure recovery of the generator, not predictive power on real applicants.
3. **No fairness audit has been performed.** Protected attributes are absent from the
   data, so disparate impact cannot be measured here. Any real use requires a
   fair-lending review under the applicable legal framework.
4. **No drift monitoring.** There is no production data pipeline, no PSI or
   population-stability monitoring, and no scheduled recalibration. Score
   distributions in deployment would be unobserved.
5. **The linear model may underfit.** A linear logit on WoE-transformed features
   cannot represent interactions or non-monotone effects; the synthetic generator is
   also linear, so its apparent metric values overstate how well this form would fit
   real data.
6. **The decision threshold is chosen for illustration**, not calibrated to costs,
   approval targets, or a loss function. Band edges are similarly arbitrary.
7. **Calibration is not guaranteed.** Predicted probabilities may not match observed
   default rates; use the metrics table rather than assuming the PD is calibrated.
8. **No authentication or rate limiting in v0.1.** The service is for local
   development and demonstration only; do not expose it to a network.
9. **Twelve features and a single global model.** No segmentation, no region or
   product-specific models, and no reject inference.
10. **Re-run `make train` before quoting any number.** Replace every `TBD` in
    Section 4.1 with the output of that run, and record the date, seed, sample size,
    and threshold alongside it.
